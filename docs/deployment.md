# Vercel Hobby deployment

## 1. Project and private storage

Import `dushyantgill/authnauthz` in Vercel and select the Next.js preset. Set the root directory to the repository root and Node.js to 24.x. The default build command is `npm run build`. The project uses the Node runtime and retains the IncomingMessage interface required by the protocol libraries through Pages API routes; the dashboard uses the App Router.

Create a **private** Vercel Blob store in the Storage tab and connect it to this project. A public store is not an acceptable substitute for protocol-state storage. Vercel supplies `BLOB_READ_WRITE_TOKEN`. One Blob store is enough for this tenant; no Postgres, KV, Redis, or marketplace DB service is required.

Use separate private stores and signing credentials for Production and Preview. Preview deployments must not operate on the production state blob. Use a stable deployment origin for each environment rather than automatically deriving issuers from request Host headers or arbitrary preview domains.

## 2. Generate and set environment variables

Run `npm ci` and `npm run setup` locally. Copy each generated value into Vercel's Environment Variables UI. For quoted values in `.env.local`, paste the contents **inside** the outer quotes, without those quotes. JSON values remain JSON strings; SAML PEM values can contain real newlines or the literal `\n` sequences generated by setup. Keep `.simulation-password` private and use its value when signing into a synthetic identity.

| Variable                   | Purpose                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------ |
| `APP_URL`                  | Stable HTTPS origin, e.g. `https://authnauthz.vercel.app`; no path, query, or fragment           |
| `STORAGE_MODE`             | `blob` for every deployment; `memory` is allowed only in local non-production development        |
| `BLOB_READ_WRITE_TOKEN`    | Credential for the connected **private** Blob store                                              |
| `ADMIN_TOKEN`              | Random administrator bearer credential; entered into the dashboard, retained only in page memory |
| `SCIM_TOKEN`               | Separate tenant-scoped provisioning bearer credential                                            |
| `COOKIE_SECRET`            | Stable random HMAC/cookie signing secret; setup produces sufficient entropy                      |
| `STATE_ENCRYPTION_KEY`     | Base64-encoded 32-byte AES-256-GCM key for persisted state                                       |
| `SIMULATION_PASSWORD_HASH` | JSON `{ "salt": "...", "hash": "..." }`; scrypt hash of the random shared simulation password    |
| `OIDC_JWKS`                | Private RSA signing JWK set; the HTTP JWKS endpoint exposes only public components               |
| `SAML_PRIVATE_KEY`         | RSA signing private key in PEM format                                                            |
| `SAML_CERTIFICATE`         | Matching X.509 PEM signing certificate; published in federation metadata                         |

The generated certificate lasts one year. Monitor its expiry and renew the certificate/trust configuration before expiry. Maintain key values across ordinary redeployments. Changing `APP_URL` changes protocol identity and requires reconfiguration of relying parties. Changing the state encryption key without migrating the state makes existing Blob data unreadable; the application fails closed rather than replacing it.

Redeploy after setting environment variables. Connect the dashboard with your admin token. An empty registration list is expected on first use. The first successful mutation creates the encrypted tenant state from the baseline; reads of an absent blob return the baseline, while storage errors are surfaced rather than treated as an empty directory.

## 3. Register applications

The Applications editor accepts the JSON shape in [config.example.json](config.example.json). Replace all example URLs and credentials. The example confidential client secret is deliberately a placeholder and must be changed. The application validates duplicate identifiers, required secrets, HTTPS redirects, SAML metadata, and required signing/encryption certificates.

### OIDC

Use issuer `APP_URL/api/t/realestate/oidc`. Obtain authoritative endpoint URLs from `/.well-known/openid-configuration`. Register exact redirect URIs and, for logout, exact `post_logout_redirect_uris`. All authorization-code clients require S256 PKCE, including confidential clients. A public client uses `token_endpoint_auth_method: "none"`; confidential clients use Basic, POST, or private-key JWT with a registered public JWKS.

Refresh tokens require `refresh_token` in the registered grant types and `offline_access` consent. Client credentials require an authenticated confidential client. Do not request an ID token from the client-credentials grant. Token consumers must verify issuer, audience, expiry, and nonce using the public JWKS for ID tokens. Access tokens are opaque and can be checked through authenticated introspection.

### SAML

Import metadata from `APP_URL/api/t/realestate/saml/metadata` into the SP. Add the SP's complete XML EntityDescriptor to `samlApps[].metadata`. Register every intended HTTP-POST ACS in that metadata and select it by URL/index in AuthnRequest when needed. Requests must carry the exact IdP Destination and be within the five-minute freshness window. RSA-SHA256-signed requests are required by default; a registration may explicitly permit unsigned AuthnRequests for an SP that needs them. Signed requests are verified whenever signatures are supplied. LogoutRequests always require signatures.

Set `encryptAssertions: true` only when the SP metadata includes an encryption certificate and its application can decrypt AES-256-GCM/RSA-OAEP assertions. Use a separate SP encryption key from the IdP signing key. Responses and assertions are signed; encryption happens before the outer response signature. Unsupported NameID/authentication-context/passive requests receive signed SAML status responses after request trust and ACS validation.

### SCIM

Use base URL `APP_URL/api/t/realestate/scim` with `Authorization: Bearer SCIM_TOKEN`. Discover advertised capabilities through ServiceProviderConfig and schemas through Schemas/ResourceTypes. Users and Groups are writable runtime copies. Group memberships and enterprise manager references use immutable SCIM resource IDs, not email addresses. Use the returned resource ETag with `If-Match` for provisioning updates. The static baseline remains locked in Git.

### WS-Fed

Import metadata from `APP_URL/api/t/realestate/wsfed/metadata`. Register the exact realm and reply URL. Passive sign-in uses `wa=wsignin1.0&wtrealm=...` with optional `wreply`, `wctx`, and `wfresh`. The app returns an auto-submitted form with `wa`, signed `wresult`, and preserved `wctx`. Choose SAML 1.1 or SAML 2.0 token format per relying party. Sign-out clears and revokes local simulator sessions. Multi-party logout propagation and active WS-Trust are outside the advertised passive profile.

## 4. Verify the deployment

Run `npm run test:blob` with the private store token and state encryption key set in your environment. This verifies actual origin reads, encrypted round trips, ETag-conditional writes, and concurrent replay reservation using an isolated object. Then register your actual test relying parties and complete a sign-in/provisioning cycle. This final integration check is required before claiming compatibility with a particular customer application or vendor product.

## Capacity and operations

As documented by Vercel in October 2026, Hobby includes 1 GB Blob storage, 10,000 simple operations, 2,000 advanced operations, and 10 GB Blob transfer per month. Check [current Blob limits](https://vercel.com/docs/vercel-blob/usage-and-pricing), since allowances can change. Each sign-in can perform multiple read/write operations for interactions, consent, sessions, tokens, rate limits, and replay records. Do not estimate capacity as 2,000 sign-ins per month. A single tenant state object also makes concurrent writers contend; this design targets low-volume simulator usage, not high-throughput identity infrastructure.

If the allowance or storage availability is exhausted, authentication/provisioning fail closed. Hobby pauses access rather than charging overages. Vercel's [Hobby terms](https://vercel.com/docs/plans/hobby) restrict the tier to personal, non-commercial use. No paid service is required by this repository; deployment use must still fit those terms.

The state object is `authnauthz/v1/realestate/state.enc.json`. Expired protocol models are removed during successful mutations, and the activity log retains only 100 entries. Back up the encrypted object and keep its encryption key securely; restore both together. No scheduled job is necessary.

An explicit baseline reset is available via `POST /api/admin/reset`, authenticated with `ADMIN_TOKEN`, with JSON `{ "confirm": "RESET SUMMIT RIDGE" }`. It restores all 267 seed identities and 185 groups, clears tokens/sessions/temporary models, retains application configuration, and records the reset event. This is intentionally not automatic on redeploy.

## Troubleshooting

- **503 temporarily_unavailable:** inspect Vercel logs for missing environment values, private Blob credentials, operation allowance, decryption errors, or contention. Storage failure never falls back to memory in deployment.
- **Client registration fails:** check exact HTTPS URLs, duplicate client IDs, secret length, and public JWKS for private-key JWT.
- **SAML invalid_request:** check signature algorithm, pinned SP certificate, Destination, issuer, request age, ACS registration, RelayState length (80 bytes), and duplicate IDs. Use the SP encryption private key for encrypted responses, not the IdP's signing key.
- **SCIM 409/412:** duplicate username or stale ETag. Read the current resource and retry the intended change.
- **OIDC invalid_grant:** expired, reused, revoked, misdirected, or incorrectly bound credential. Reuse of authorization codes/refresh tokens revokes the associated grant family. Begin a new authorization flow.
- **Local data disappears:** memory mode is intentionally ephemeral. Select private Blob mode to retain runtime changes.

## Account domains

After connecting the dashboard with `ADMIN_TOKEN`, open **Account domains**. Enter separate domain suffixes for employees and vendors/contractors (without `@` or a URL), then save. Existing usernames and work emails change atomically; IDs, hierarchy, and memberships remain unchanged. Domains persist in the encrypted Blob configuration and are retained when resetting the directory. The locked source dataset is unchanged. Update relying-party account mappings as needed and start a new sign-in to receive updated claims; previously issued tokens retain their original claims until expiry. SCIM clients explicitly choose usernames for newly provisioned accounts; saving domains reapplies the suffix to all current Employee/Contractor accounts.

The admin token authorizes reads of live state and application registrations, configuration changes, and explicit directory resets. It is separate from a simulated user's login password and the provisioning token. The dashboard keeps it only in page memory; disconnecting or refreshing removes it from the dashboard.
