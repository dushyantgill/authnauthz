# Real Estate group strategy

The 267-identity archetype has 238 employees and 29 embedded vendors. Its locked baseline contains 185 groups: 9 organization, 27 department, 34 location, 78 direct-report, 9 leadership, 12 project, 7 role, 7 application, and 2 workforce groups. This is a plausible starting count, not a universal industry benchmark. The direct-report groups account for 42% of the baseline; raw count overstates the depth of its access model.

Create groups for a defined access or collaboration purpose, not to meet a numerical target. Keep the current 185-group seed stable. Expand a runtime scenario through SCIM after an approved resource inventory. Every group needs an owner, description, purpose, membership method, access mapping, review interval, and retirement trigger. Administrative metadata belongs in the scenario manifest; do not invent SCIM attributes without advertising their extension schema.

| Layer                    | Naming examples                                                         | Membership / purpose                                                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workforce and structure  | WF-EMPLOYEES, ORG-FINANCE, DEPT-TREASURY                                | Attribute driven; eligible active people only; administrative structure alone should not imply privileged access                                      |
| Business role            | ROLE-LEASE-ADMINISTRATORS, ROLE-CONSTRUCTION-PMS                        | Job function and manager approval; employees and sponsored vendors where appropriate                                                                  |
| Application entitlement  | APP-YARDI-READERS, APP-YARDI-LEASE-ADMINS, APP-PROCORE-PROJECT-MANAGERS | One group per independently assignable application role; nest approved role groups only when the receiving application supports transitive membership |
| Property / asset scope   | ASSET-RIVERFRONT-OPERATIONS, ASSET-RIVERFRONT-FINANCE-READERS           | Named property assignments; operational access separated from financial access                                                                        |
| Development project      | PROJECT-RIVERFRONT-DESIGN, PROJECT-RIVERFRONT-COST-CONTROL              | Project lifecycle, explicit assignments, sponsor, end date; close out at project completion                                                           |
| Approval and segregation | APPROVAL-INVOICE-TIER-1, APPROVAL-CAPEX-COMMITTEE                       | Documented authority thresholds; requester/approver and vendor-master/payment separation                                                              |
| Restricted access        | ACCESS-LEGAL-MATTERS, ACCESS-HR-CASEWORK                                | Explicit need-to-know, legal/HR owner review; membership never labels immigration or survivor status                                                  |
| Privileged operations    | PRIV-IDP-ADMINS, PRIV-YARDI-ADMINS                                      | Small, explicit, separately reviewed; no broad department or contractor inheritance                                                                   |
| Collaboration            | COLLAB-INVESTMENT-COMMITTEE                                             | Distribution/team access only; distinguish security entitlements from communication groups                                                            |

Phase 1: inventory seven seeded applications and their actual assignable roles. Split broad APP-*-USERS groups into readers, contributors, approvers, and administrators only where the application supports these permissions. Yardi can distinguish accounting, lease administration, reporting, and property management; Procore can distinguish project managers, cost control, subcontractor collaborators, and viewers. Validate each against the integration's role model before provisioning.

Phase 2: inventory properties and active developments. Add asset and project scope only for resources represented in the scenario. Model vendor sponsorship and expiry explicitly; workforce classification alone grants no property or privileged access. Add approval and restricted-access groups after reviewing conflicts and access boundaries.

A planning scenario could add 20–35 application-role groups, 15–30 asset/project groups, 8–15 approval/restricted groups, and 5–10 privileged/collaboration groups: about 233–275 total if all additions have distinct purposes. These are design estimates, not evidence that every real-estate company needs that many groups. Reuse existing groups where meanings overlap; remove obsolete groups rather than accumulating them.

Validate unique immutable IDs/names, existing member references, acyclic nesting, no unintended vendor privilege inheritance, actual effective membership at each relying party, and no conflicting approval rights. Review privileged groups monthly, business access quarterly, and project groups at milestones. Disablement removes eligibility; vendor assignment expiry and project completion trigger removal. Deletion follows access review and audit retention. Add lifecycle metadata and scenario generation tooling as a separate implementation before relying on automatic reviews/expiry; the current simulator does not claim to automate those policies.
